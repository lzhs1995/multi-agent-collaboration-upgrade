# Original startup-failure continuity — opt-in prototype

2026-10-21. This separate contract addresses an original Codex failure before
its readiness probe while both original Claude clients remain source-verified.
It does not manufacture healthy-trio adoption or empirical acceptance. The
initial supported case is an original terminal401/402/403 on the pinned Codex
model, followed by neither readiness execution nor later recovery/model input.
Retryable failures, actual process/session loss and post-startup recovery are
not implemented by this prototype; the broader three-mode task remains open.

## Explicit source and authorization

Materialization requires both `--register-private-continuity` and the new
`--register-startup-continuity`. Without the new opt-in, the original automatic
adoption requirement is unchanged. The opt-in does not launch a client, enroll
an inquiry, publish adoption, create a child or install shared hooks/CURRENT.
Previously frozen controllers cannot be hotpatched or retrospectively opted in.

The external publisher requires a fresh pinned `experiment-inspect` result,
the same three original launch records/PIDs/births/workspace/session identities,
the original Codex read-only thread capability, private configuration/model
pins, complete journals and correlated actual Claude readiness hooks. An old
inspector result cannot substitute for current native input identity checks.

The user authorization comes from an exact original account-native user record
outside the experimental clients. It retains session metadata, canonical path,
device/inode, offset/length, record SHA256 and exact user-text SHA256. An
experiment's own startup prompt, assistant text, queued/tool-result attachment,
sidechain, copied file, different inode, wrong hash or wrong original session
cannot self-authorize fallback. Production obtains account HOME/UID from the
immutable original context; there is no public HOME/fixture override.

The same frozen controller verifies the contract in a separate, fixed,
non-model Python process under its original macOS control Seatbelt. No
`sys.modules` swapping, replacement SDK, model caller or second evaluator is
introduced. The existing native terminal/user-message grammar is shared through
`upgrade_native_outcomes.py`; it independently grants no input authority.

## Availability is not a readiness label

Codex's initial terminal must match its original task_started turn, pinned model
context, exact startup user prompt and one concrete permanent API status. Text
mentioning402, a boolean/string status, internal retry noise, a half-open turn,
unknown terminal, executed probe or later model change cannot establish this
startup case. The caller retains the actual original native reference.

Each Claude must also have an original complete API terminal attached to the
same session's authentic parent chain. A tool return alone is insufficient.
The whole current captured interval remains bounded and model-checked; native
model drift or an unproven later availability state refuses new use.

`startup-continuity.json` is exclusively published read-only under the original
runtime's live-control directory. Its schema explicitly records
`production_adoption=false` and `input_operations=0`. It is not `adoption.json`.
Benchmark/campaign validators still require their original healthy trio.

The input gate uses the source-verified contract only for the two original
ready Claude endpoints. It checks both fresh process/birth/root/kernel bindings,
the original workspace/pane and stop boundary before returning to the existing
MAC one-input/native-receipt path. It cannot route to the failed Codex or an
external/replacement endpoint and never itself sends a message.

Native continuity and the existing child service may refer to this explicit
alternative authority. The child task ID and native authorization must equal
the startup contract. The same whole-task ledger, original two parent IDs,
maximum two unconsumed children and exact parent FULL-read/SHA-consume semantics
remain unchanged; a new task label cannot create another empty ledger.

## Separate startup interval, same original evaluator

An ordinary native registration continues to count only terminals after its
fixed registration fence. A startup-continuity registration additionally uses
the explicitly labeled `upgrade-startup-native-continuity-observations-v1`
interval with `ORIGINAL_STARTUP_NOT_ADOPTION_EPISODE`. It preserves the original
registration fences on disk and in the result; it does not rewrite old fences
or mix initial failure evidence into a historical adopted episode.

This interval is independently rederived before and after invoking the actual
complete original `collaboration_continuity.py`. Pending/partial/exhausted
intervals cannot invoke it. The resulting CLAUDE_PEER decision remains advisory:
it is not an actual peer handshake, native child creation, ownership transfer,
resource release or supervisor acceptance.

## Public entry and validation boundary

The external script accepts only hash-pinned register requests and verify
registrations. Request schema is
`upgrade-startup-continuity-register-request-v1`, containing exactly `runtime`,
`inspection`, `task_id`, `native_authorizations`,
`automatic_fallback_authorized` and `schema`. The CLI exposes no clock, model,
HOME, fixture, outcome/status, input or replacement override.

test also passed. These are explicit working-source results, not a frozen full
suite, independent review, installed skill or live acceptance claim. Failed
