# Additive TASK capabilities

The original TASK execute catalog has no inquiry reply or continuity write operation. A task pack alone cannot add those capabilities. These modules provide an explicit controller extension on the same adopted task, with separate intent and result files. They do not amend its registration, attempt ledger, UNKNOWN results, budget, or frozen campaign.

Codex 0.164.0 exposes `dynamicTools` on `thread/start`, but not on `thread/resume` or `turn/start`. The extension therefore uses the existing `upgrade_collaboration.execute` tool. Its operation ID is `extension:<extension_id>:<operation_id>`; the original catalog remains unchanged.

## Controller integration

The existing retained controller owner must deliberately call these APIs at a normal closed turn. This is executable controller integration, not automatic activation on import:

```python
from upgrade_task_capability_extension import register_extension
from upgrade_task_capability_service import CapabilityService

# request_ref is the SHA/byte pin of the explicitly accepted request below.
registration_ref = register_extension(request_ref)  # no model input
capabilities = CapabilityService.activate(original_task_service, registration_ref)
while not capabilities.closed:
    capabilities.pulse(seconds=1)
```

`activate` requires the original `TaskService`, `TaskCampaignGate`, client, adoption, native server identity and exact normal completion. It uses the original next-turn intent path to exclude a competing continuation. It sends at most one `turn/start` on the same thread. The previous ledger is opened read-only and its complete snapshot must stay unchanged. Pending original calls block takeover; historical UNKNOWN calls remain recorded.

The owner routes subsequent records to this service for that auxiliary turn. The old service must not simultaneously consume the same socket. The service handles exact dynamic-tool calls and their completions; ordinary notifications are observed. A duplicate call ID is rejected before dispatch or response. Uncertain activation, operation or response retains its intent and cannot be resent. A durable `service-owner.json` is claimed once per activation. Reconstructing another service object is refused even in the same process: its empty pending map cannot replace prior activity, UNKNOWN, or normal completion. Read-only reconciliation must inspect the original records; this API provides no service-resume operation.

The original model uses the exact script generated by `invocation_script(extension_id, operation_id)`, for example:

```javascript
const result = await tools.upgrade_collaboration__execute({operation_id:"extension:accepted-scope:read"}); text(result);
```

## Accepted request and authority

`upgrade-task-capability-request-v1` has exactly these fields:

| Field | Required source |
| --- | --- |
| `extension_id` | Unique name; an existing extension directory cannot be reset. |
| `base_registration` | Original `upgrade-task-operations-v3` file pin. |
| `base_ledger` | Original absolute path, device and inode. |
| `runtime`, `adoption` | Original runtime and actual adopted session pins. |
| `previous_completion` | Original received normal `turn/completed` record and RPC peer. |
| `authority` | Explicit versioned authority file pin, described below. |
| `operations` | Up to 64 fixed `{action, payload}` operations with no original-catalog ID collision. |
| `schema` | `upgrade-task-capability-request-v1`. |

Each file pin is `{path, bytes, sha256}`. The scope hash is `scope_digest(request)`, which excludes only `authority`. The original Codex assistant must emit one `upgrade-task-capability-acceptance-v1` JSON with `task_id`, `extension_id`, `scope_sha256`, source-authority hash and `budget_sha256`; an echoed user/tool message does not count.

Authority v1 uses `native_authorizations` verified by the existing native-user verifier. Authority v2 instead uses `goal_authorization={evidence, context}`. Its source is the explicitly separate native Goal event plus the bound attachment's original complete command execution and model-visible output. It is never relabeled a native user message. The v2 assistant acceptance binds `goal_authorization_sha256` to the entire evidence/context object. Context contains `original_session_id`, `goal_created_at`, `attachment_bytes` and `attachment_sha256`. Both versions preserve the original whole-task budget pin.

Missing authority, adoption, acceptance, native proof or normal completion is a rejection; placeholders cannot activate anything. Preparing these pins does not authorize a new campaign or revive a prior attempt.

## Inquiry operations

The channel payload is explicitly versioned as `upgrade-task-inquiry-channel-v2`. It has `schema`, `lane` (`claude_a` or `claude_b`), `episode={path, episode_id, registration_token}`, an immutable `enrollment` pin, `channel`, and `slot` (1 or 2). Slot 2 also has `previous_read_operation_id`, pointing to slot 1 for the same lane and exact episode/enrollment/channel. Every `inquiry-answer` adds `read_operation_id` referring to its exact read payload. A registration may contain at most four read/answer pairs: two per original Claude lane. It cannot mix this contract with the older pinned-request contract.

The `channel` string must equal the path derived from the original runtime state root and registered caller/supervisor; it is not an arbitrary file selector. No future marker or content hash is needed during registration. Each read saves its validated original ask, complete request, enrollment binding and observation SHA in an exclusive `inquiry-snapshot.json`. The read result returns the snapshot pin and full body. Per-episode slot and marker intent records are shared across extensions, so changing an extension or operation name cannot reset a slot or reread the same marker.

The older payload with an immutable `request` pin remains supported for its original single-request scope. It is not the two-cycle interface.

The request is the original producer's `executor-reask-current-v2` file at `supervisor-inbox-v1/<supervisor SHA>/<caller SHA>.json`. File-only asks do not create an idle request-v4 file and have no `ask.record` field. Validation binds the canonical channel path, `channels.written`, complete `request` text, `ask.text_sha256`, original marker, epoch, FILE_ONLY outcome and zero terminal inputs. Enrollment must retain the exact immutable continuation grant and original token.

The ask must occur at or after its original `due_epoch`. For attempts after the first, the preceding retained ask must prove at least 60 seconds spacing. A missing previous ask cannot be inferred. A first ask alone proves no two-cycle result. The original stop file or expired grant prevents dispatch.

Read returns the entire body and hash. Answer requires the original complete `functions.exec` read output followed by a unique assistant JSON with schema `upgrade-task-inquiry-answer-v1`, `task_id`, `extension_id`, `operation_id`, `read_operation_id`, `body_sha256` and `reply`.

The reply includes exact `marker`, `caller_surface_uuid`, `supervisor_uuid`, `task_id`, `episode_id`, `status` and a concrete `trigger`. ACK uses those seven fields. BLOCKED, WAITING_DEPENDENCY and SOLO additionally require `owner == supervisor_uuid` and finite UTC `next_due_epoch`/`deadline_epoch`, with `0 < due <= deadline`. The original template's optional `overall_task` is accepted only when it exactly matches the enrolled continuation. TASK and DISPATCHED are not supported here: a status reply cannot create a dispatch.

The canonical reply hash matches the original controller's sorted compact UTF-8 JSON. Publishing uses one exclusive intent per original caller/episode/marker across extensions and one exclusive original mailbox file. The extension never consumes the executor's reply, rearms its episode, releases a reservation or sends terminal input. Executor consumption must use the original controller and original identity.

An answer binds only its read snapshot. The original episode must still authenticate that issued HMAC marker and show that its ordinal has not been consumed; a later channel replacement does not retarget or invalidate the saved read. Slot 2 requires slot 1's complete native read/answer outputs, the original canonical consumption receipt, its matching episode history and original executor session, and a new issued ask at least 60 seconds after the first. Its original consumption time must fall between the two asks. Neither current-channel replacement nor ordinary consumption changes the registration's immutable scope.

The original scheduler and foreground consumer remain responsible for issuing the next ask and consuming the reply. Slot 2 must be invoked after those facts exist; invoking it too early fails its one-attempt operation rather than starting a scheduler or inventing consumption. Actual two-cycle acceptance still requires real timing and authenticated execution.

## Continuity and validation limits

Continuity actions dispatch only to the fixed continuity module, with the retained scope/checkpoint/budget contract. See `task-continuity-capability.md`. The separate Claude peer route is a distinct integration; the Codex service itself requires an in-progress original Codex turn and cannot stand in for a failed Codex.

The offline suite exercises original-format RPC, SQLite snapshots, complete native transcript outputs, model-authored statement distinctions, mailbox writes, native completion, closed-turn activation, duplicate rejection and UNKNOWN retention. Kernel observations and actual clients are fixtures. A separate private probe executes selected original controller functions in temporary directories, including producer/binding/reply validation and the authenticated consume core; it does not import or modify the live controller. Neither result proves a real scheduler cycle, Stop hook, foreground identity, model execution, third-state takeover, or business acceptance.
